# Приём лейблов и управление доступом

Реализация ТЗ заказчика «Label Registration & Onboarding» (файл прислан 22.08.2026,
три листа: воронка регистрации, Users & Access, Access & Restrictions).

## Путь лейбла

```
заявка → в работу → (запрос данных ⇄ ответ) → одобрена
      → аккаунт создан со статусом review (войти можно, работать нельзя)
      → KYC + права + подписанный договор
      → админ жмёт «Активировать аккаунт» → status = active
```

Ключевое решение: одобренная заявка **не** даёт рабочий аккаунт. Войти в кабинет
можно сразу — иначе онбординг негде проходить, — но загрузка релизов, перенос
каталога, паблишинг, снятия и заявки на выплату закрыты до активации
(`requireActiveAccount` в `lib/account-access.ts`).

## Таблицы

| Таблица | Зачем |
|---|---|
| `signup_requests` | заявка + анкета (~20 полей), IP, внутренняя заметка, переписка «дошлите данные», токен доступа |
| `account_restrictions` | по строке на закрытую функцию; снятие ставит `lifted_at`, история остаётся |
| `account_violations` | нарушения; на риск влияют только `confirmed` |
| `contracts` | версии, статусы, подпись кодом из письма, расторжение |
| `rights_verifications` | одна строка на пользователя, переподача перезаписывает |

Миграция — `lib/db/migrations/0033_label_onboarding.sql`, идемпотентная.

## Ограничения доступа

Ключи функций — `RESTRICTION_FEATURES` в `lib/db/src/schema/account_restrictions.ts`:
площадки (`dsp:*`), Content ID (`rights:*`), дистрибуция (`dist:*`), деньги (`fin:*`),
`account:full_suspension` (закрывает всё разом).

Ограничение — не украшение интерфейса. `requireFeature(...)` висит на реальных
маршрутах:

- `POST /releases` → `dist:upload`
- `POST /releases/transfer-imports` → `dist:transfer`
- `POST /takedowns` → `dist:takedown`
- `POST /payouts` → `fin:payout_requests`
- `POST /publishing/works` → `dist:publishing`
- отправка в Broma16 проверяет `dist:delivery` у владельца релиза (пуш делает
  админ, а ограничение стоит на клиенте — иначе его было бы легко обойти)

Ограничения на площадки и Content ID пока только фиксируются: чтобы они реально
действовали, нужно уметь отзывать конкретный аутлет в Broma16 — API это не даёт.

## Риск

Три подтверждённых нарушения → `riskLevel: high`. Автоматических блокировок нет:
заказчик отдельно просил, чтобы конкретные ограничения выбирал администратор.

## Экраны

- `pages/users/index.tsx` — список: колонки договора, прав, риска, вкладка «Договоры»
- `pages/users/[id].tsx` — карточка: обзор, доступ, нарушения, договоры, права,
  чек-лист активации
- `pages/signup.tsx` — анкета (раскрывающийся блок «Подробнее о каталоге»)
- `pages/signup-request.tsx` — публичная страница «дошлите данные» по токену
- `pages/contracts/index.tsx` — договоры глазами клиента, подписание кодом
- `pages/profile/_rights-tab.tsx` — клиент подтверждает права

Фронт намеренно простой: `api()` + `useState`, без генерации клиента и без
стора — эти экраны будут править чаще, чем читать.

## Подтверждение контактов

Почта — ссылка из письма, токен одноразовый, живёт сутки. Маршрут подтверждения
подключён **до** `requireAuth`: письмо часто открывают там, где не залогинены.

Телефон не подтверждается: SMS-шлюза нет. `POST /users/me/verify-phone/send`
отвечает 501 с объяснением, интерфейс сразу показывает «проверяет менеджер».
Когда появится шлюз, менять надо только этот маршрут — колонки в базе готовы.

## Что осталось за рамками

- **подтверждение телефона** — нужен SMS-шлюз, это платная услуга и решение заказчика
- электронная подпись — только код из письма (удостоверяющего центра у заказчика нет)
- загрузка PDF договора: поле `object_path` есть, интерфейса загрузки нет
- ограничения по отдельным площадкам не доезжают до Broma16 (см. выше)

Статус KYC «In Review» из ТЗ отдельной строкой не заводили: ему соответствует
существующий `pending` — документы поданы и ждут проверяющего.
